# Bounded post-bind network-failure retry and isolation probe

The independent `--network-retry --media-dir <generated-directory>` mode requires generated 180-second H.264/AAC media and the owned synthetic fixture on port 18961. It uses the default product player owner and PlaybackCoordinator. It does not start or change the official validation server, another application's sessions, or global network settings.

The range proxy permits only the first 512 KiB and the block-aligned MP4 moov metadata region during initial playback. Other ranges wait behind its explicit gate. The report retains offsets, byte counts, status codes, phases, and completion without URLs or authentication headers. The middle byte must remain undelivered and the 90-second target outside native buffered ranges before faulting. The media is 180 seconds long; each proxy request still has its existing 30-second timeout.

After native playback advances and pauses, the probe records the original playback/session identity, actual player/source references, and source binding. It captures all seven native event delegates while that original source is still bound, before starting the cold seek or releasing HTTP 503. A missing capture, prior failure, or missing binding fails the observation.

The coordinator seeks to the cold 90-second target and the proxy releases pending/new requests with real HTTP 503 responses. Valid media remain unchanged. The original strict classification gate is retained: a completed cold HTTP 503 with zero forwarded media bytes, native-engine NetworkFailure, and confirmed product-relay NetworkFailure must all be observed. A different classification or an already-buffered target fails.

The engine Failed event synchronously records that the original playback and exact player/source are still bound. Product Fail publishes this event before retirement; inspecting a later recovery cannot supply that evidence. The raw Windows error/HRESULT remain independently recorded when emitted. A missing source-bound observation fails the post-bind gate even if retry becomes available. The causal failure is always real HTTP 503, never a synthetic Failed event.

Only after that gate offers a recoverable failure does the probe restore the proxy and call RetryAsync with the observed recovery ID. Retry must create new playback/server-session IDs, bind a source, reach the recorded nonzero target, preserve paused intent, and consume recovery. No additional PlayAsync is used for isolation: it must inspect this exact retry replacement, keeping the existing two-proxy-binding contract.

After pause and 200 ms of completed-API quiet, the probe saves replacement player/source references, logical IDs, native and engine positions, volume/mute, and engine/API boundaries. It deliberately invokes the original retired session's seven captured native delegates and nine old-ID commands. Both replay helpers require a retired session. Failed receives null synthetic arguments only after that guard; its captured product delegate must return on the retired-session check before reading them. This later deliberate replay is separate from the genuine original transport failure and does not claim naturally delivered late callbacks.

The post-retry replay window requires all of the following:

- Exactly seven completed native-delegate invocations and nine completed old-ID commands.
- Unchanged replacement playback/server-session/source IDs and the same bound player/source objects before and after replay. The product may reuse its player owner across sessions; old/new player objects are not required to differ.
- Native and engine state remain paused, native position has zero drift, and the engine position remains unchanged.
- Native and engine volume/mute remain unchanged, with recovery still consumed.
- No retired-playback, Failed, or Ended engine event. Only replacement-ID StateChanged/PositionChanged notifications that retain Paused and the exact saved snapshot position are allowed; total, allowed, and unexpected counts are recorded. API activity may contain only successful replacement-session Progress/TimeUpdate reports; null event names, control reports, or new negotiation fail.

Completed-request counts and report-event counts are independently observed and include different operation sets. Their delta comparison remains diagnostic and is not a pass requirement. The actual report-event suffix and unchanged negotiation count are required. A quiet API suffix is valid because the 650 ms observation need not include a one-second periodic report. The paused replacement is then resumed and its actual native clock must advance. Both original and replacement sessions retain successful ordered Start/Stop requirements, old proxy bindings must issue no new request after retry, and final native/API/media traffic must remain quiet. No original assertion or classification threshold is relaxed.

Final cleanup separately attempts observer detachment, coordinator and native-engine disposal, cold-seek drainage, logout, and proxy disposal. Cleanup failures are retained while the remaining cleanup steps are attempted. Coordinator disposal, completed native disposal, cleared owner, logout, and disposed proxy must all be established before PostBindLateFailureGateStatus becomes Passed. Timeout, observer, replay, or cleanup errors remain failures in their new report.

The report distinguishes original playing/paused position, requested seek target, SeekCompleted events, failure snapshot, and recovery target. An unsuccessful seek cursor is not a decoded or displayed frame. This one bounded post-bind recovery/isolation scenario does not certify presented pixels, audio devices, broad network faults, or long-running resources. Historical failed classification and isolation reports remain unchanged and require their original source/executable identities.
