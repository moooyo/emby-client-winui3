The future control dispatch is `--output-dir <fresh-directory> --complex-subtitle-http-profile-control --credentials-file <owned-file> --fixture-manifest <bound-manifest> --case <ass-styled|pgs-bitmap>`. It reuses the existing identity, manifest, actual API source/track binding, native event observation, PNG, and root visual-confirmation contracts. The report has `ExecutionMode: ProgressiveHttpProfileControl`, `ProfileControl: true`, and can finish successfully only as `ControlPassed`, never a default-profile `Passed` result.

The request changes only each default TranscodingProfile's `Container` from `ts` to `mp4` and `Protocol` from `hls` to `http`. All other profile fields remain from `ConservativeDeviceProfile.Create()`. `ForceTranscoding` remains false, audio selection stays automatic, external WebVTT stays disabled, and the original explicitly selected subtitle index is retained. The main application default profile is unchanged. No HLS response, HTTP 500, or existing failure receipt is rewritten or ignored.

The real product engine uses `ProgressiveHttpRelay` only for a non-HLS Transcode request with `TimelineKind.ProgressiveSegment`. Its local URL is created using the negotiated `Source.TranscodingContainer`, not the original MKV container. FullSource requests retain the existing range relay, and HLS retains its adaptive path. The session owns the new relay; retirement first cancels its lifetime, and drainage awaits relay disposal before the scoped transport is disposed. MediaSource, player-owner, callbacks, and server-session ownership retain their existing lifecycle. A queued Ended callback first checks an already recorded relay failure and reports failure instead of publishing a successful end.

The enabled control starts at source time 41 seconds. It requires an actual Transcode/Encode progressive route, the product progressive relay, MP4 transcoding container, request `InitialPositionTicks=0`, offset 41 seconds, and a real paused native clock near zero. The report retains both engine position and `SourcePositionTicks = TimelineOffsetTicks + PositionTicks`; the offset is added exactly once. Pause drift uses two present native samples only. A missing sample has null drift and cannot pass. The default HLS mode continues to require FullSource with zero offset and its unchanged HLS route checks.

The first two screenshots retain the existing Enabled and Disabled protocol. `ChangeSelectionAsync` explicitly disables subtitles with index -1 while preserving the actual source position and pause intent. If the server legitimately selects DirectStream for the disabled source, the report records that result and verifies its full-source range relay. It does not force that request back to progressive HTTP or count a DirectStream tail as proof of the new streaming path.

The third observation, `TailFrame`, runs on an actual progressive HTTP source. If Disabled selected DirectStream, the control explicitly selects the original subtitle again with the same HTTP profile and `ForceTranscoding=false`, producing a third encoded session. Otherwise it reuses the disabled progressive session. The initial paused observation and actual delivery are retained. It resumes normally, waits for a playing source position within the final 750 ms, then pauses and applies the same native position/dimensions/drift checks. It does not set the clock to manufacture a tail observation.

For a later authorized visual run, `complex-subtitle-tailframe-ready.json` requires a fresh PNG and a matching finish with `Phase: TailFrame` and exactly `ConfirmedFeatureIds: ["video-frame-visible-near-end", "subtitles-absent-after-cue"]`. These features mean a video image is visible at the separately recorded native near-end position and the 35-45 second cue is absent. The old 41-second fixture reference is contextual, not an exact expected tail-frame image. This does not claim pixel-perfect frame identity or OCR. The reference, Enabled screenshot, and Disabled screenshot cannot substitute for the TailFrame screenshot. `Wait-ComplexSubtitleReady.ps1` accepts `-Phase TailFrame` and does not open an active report.

After that confirmation, the control resumes and requires an actual Native Ended event, a source-relative end within one second of the manifest runtime, the matching Coordinator Ended event, and a fully drained session with no bound player/source. A recorded failure aborts this wait. Final cleanup verifies two or three unique Start/Stop pairs according to the actual graph count and exactly one ordered StopEncoding per Transcode session. The same session can supply Disabled and TailFrame observations; it is counted once. Player-owner disposal and logout remain final requirements.

This is one prepared source-start/control sequence. Start zero, resource loops, broad server compatibility, and long-duration stability are separate future stages.
